## 1. Три блокера — закрыть в первую очередь, до содержательной работы над контентом

При построчном чтении текущего кода (`js/main.js`, `sitemap.xml`, JSON-LD на страницах городов) нашлись три проблемы, которых не было в частях 1–3 и которые важнее любых контентных правок:

### 1.1 Критично: форма заявки ни на что не отправляется
В `js/main.js` буквально написано в комментарии: *«Book form: local "sent" state (no backend wired up yet)»*. Форма на главной странице (`#book-form`) при отправке просто показывает блок "Thank you!" на клиенте и **никуда не передаёт данные** — ни на email, ни в CRM, ни в таблицу. Это значит: если сейчас с сайта действительно нет лидов — весьма вероятно, что дело не (только) в SEO, а в том, что форма физически не работает, и все, кто её заполнил, считают, что заявка ушла, хотя это не так. **Это нужно чинить в первую очередь, независимо от остального этапа.** При переносе на Next.js — реализовать реальный backend: Route Handler (`app/api/book/route.ts`), который отправляет заявку на email владельца (например, через Resend/SendGrid) и/или в вебхук CRM. Это минимально достаточное решение для дня 1; полноценная онлайн-запись с реальными слотами (Housecall Pro / Jobber — уже упомянуты как вариант в Части 1, раздел 8) остаётся отдельным решением, которое нужно от владельца.

### 1.2 `sitemap.xml` покрывает меньше четверти сайта
Текущий `sitemap.xml` содержит всего 6 URL (главная, about, brands, for-business, ровно одна страница техники из 12, ровно один город из 5) — отсутствуют 11 страниц техники, 4 из 5 городских страниц, `towns/index.html`. При переносе на Next.js sitemap должен генерироваться автоматически (`app/sitemap.ts`) из тех же данных, что и роутинг — тогда рассинхронизация станет структурно невозможной.

### 1.3 Домен и NAP: подтвердить перед запуском
Как уже отмечено в Части 3 — сайт сейчас на `zholudz.com/ekfix_redesign`, canonical и JSON-LD везде указывают на `ekfix.us`. Дополнительно нашлось: на страницах городов (`towns/charlotte.html` и, вероятно, остальные) название бизнеса в JSON-LD — **«EK Global Appliance Repair — Charlotte, NC»**, а не «EK Global», как на главной и как требует NAP-консистентность из Части 3. Это нужно унифицировать при переносе — единое название бизнеса из одного источника данных на всех страницах.

## 3. Технологический стек и архитектура

**Стек:** Next.js (App Router) + TypeScript. Рендеринг — статическая генерация (SSG) для всех страниц на этапе сборки: контент не настолько динамичен, чтобы требовать SSR на каждый запрос, а SSG даёт наилучший Core Web Vitals результат почти бесплатно (что напрямую закрывает требование Части 3, раздел 4). Инкрементальная регенерация (ISR) можно рассмотреть позже для блока отзывов, если он будет обновляться без пересборки.

**Сохранение дизайна — главное техническое решение этого этапа:** переносить `css/style.css` в проект **практически без изменений** как глобальный CSS-файл (`app/globals.css`), а не переписывать в Tailwind/CSS-in-JS. Существующая вёрстка (все блоки `index.html`, `for-business.html`, `about.html`, `brands.html`, страниц техники и городов) переносится в React-компоненты с теми же самыми классами и структурой DOM, которые уже есть — это единственный способ гарантировать «без ущерба дизайну» буквально, а не по описанию.

**Структура роутов (App Router):**
```
app/
  layout.tsx                      — Header + Footer + шрифты (переносятся 1:1 из текущей разметки)
  page.tsx                        — главная (index.html)
  about/page.tsx                  — about.html
  brands/page.tsx                 — brands.html
  for-business/page.tsx           — for-business.html (расширяется по Части 2)
  appliance-repair/
    [slug]/page.tsx                — 12 страниц техники, generateStaticParams из данных ниже
  towns/
    page.tsx                       — towns/index.html
    [slug]/page.tsx                 — только для городов с уже готовым полным контентом (см. п. 5)
  api/
    book/route.ts                   — обработчик формы заявки (см. п. 1.1)
  sitemap.ts                        — автогенерация из данных ниже
  robots.ts
```

**Слой данных (единый источник правды — решает и NAP-консистентность, и рассинхронизацию sitemap/GBP):**
```
data/
  business.ts     — название «EK Global» (ровно одно написание), телефон, часы работы, адрес (город/регион, без улицы — SAB), areaServed (см. п.5 — не более 20 записей, синхронно с GBP)
  services.ts      — 12 услуг + новые коммерческие категории из Части 2, блок 7.3 (Commercial Refrigeration, Commercial Dishwasher/Warewasher и т.д.)
  towns.ts          — список городов с флагом isFullPage (топ 5-8, по правилу Части 1) и остальные — просто текст без роута
  reviews.ts         — отзывы (реальные, с привязкой к городу/технике)
  brands.ts           — бренды с логотипами, разбитые на коммерческие/премиальные/массовые (порядок по Части 2, блок 7)
  b2b-segments.ts      — вертикали для «Кого мы обслуживаем» и `for-business.html` (Части 2, блоки 7.2 и 8.2)
```
Все JSON-LD-компоненты, `<title>`/`<meta>` через Next.js Metadata API, sitemap и сама вёрстка страниц читают данные из этих файлов, а не хардкодят текст по месту — это структурно исключает повторение проблем из п. 1.2 и 1.3.

**Компоненты (маппинг из существующих CSS-классов — переносятся как React-компоненты с теми же классами, без нового визуального языка):**
`Header`, `Footer`, `Hero`, `WhoWeServeGrid` (новый блок из Части 2, п.7 блок 2, на базе `.audience-card` + новый модификатор `.card-grid-4` — единственное согласованное расширение CSS), `RepairGrid`/`RepairCard`, `FamilySection`, `ReviewsGrid`, `BrandGrid` (с сортировкой commercial-first по Части 2, блок 7), `ChipRow` (переиспользуется для «Trust/compliance» блока, industries, city chips), `ProblemCardGrid` (уже используется на страницах техники и about.html), `CtaBand`, `FaqAccordion` (на основе `.faq-item`, уже есть на страницах техники — переиспользовать 1:1 на `for-business.html`), `BookForm` (+ новое поле «I'm contacting you as a...» по Части 2, п.7 блок 9), `JsonLd` (общий компонент, принимает тип и данные из `data/business.ts`/`data/services.ts`).

**Изображения:** перенос `assets/images/*.webp` в `public/images/`, использование `next/image` с явными размерами вместо голых `<img loading="lazy">` — сохраняет ленивую загрузку, добавляет автоматическую оптимизацию.

## 4. Как контентные инструкции из Частей 1–2 превращаются в Next.js-реализацию

Части 1 и 2 написаны в терминах конкретных HTML-секций и CSS-классов статического сайта — это не нужно переписывать заново, инструкции остаются валидными **как содержание и порядок блоков**. Разница только в реализации:

| Инструкция из Части 1/2 | Как реализуется в Next.js |
|---|---|
| «Секция `#who-we-serve`, `.card-grid-4` из 4 карточек» (Часть 2, блок 7.2) | Компонент `<WhoWeServeGrid segments={b2bSegments} />`, данные из `data/b2b-segments.ts`, порядок массива = порядок карточек (юрлица первыми) |
| «В `<select id="appliance">` добавить коммерческие пункты» (Часть 2, блок 7.3/7.9) | Список опций генерируется из `data/services.ts` (единый источник для сетки услуг и формы — не два места с риском рассинхронизации) |
| «12 страниц техники + правила против тонких страниц городов» (Часть 1, разделы 3–4) | `generateStaticParams()` в `appliance-repair/[slug]` — из `data/services.ts`; `towns/[slug]` генерируется **только** для городов с `isFullPage: true` в `data/towns.ts` (топ 5-8) — остальные физически не получают роут, что технически гарантирует соблюдение анти-doorway правила из Части 1 и Части 3 |
| «FAQ-блок на `for-business.html` через `.faq-item`» (Часть 2, блок 8.7) | Тот же компонент `<FaqAccordion items={...} />`, что уже используется на страницах техники — плюс `<JsonLd type="FAQPage" items={...} />` рядом |
| «Сортировка `.brand-grid` commercial-first» (Часть 2, блок 7.7) | Сортировка в `data/brands.ts` один раз — используется и на главной, и на `brands.html` |

## 5. SEO-техническая имплементация (из Части 3, в терминах Next.js)

- **Schema:** `<JsonLd>` компонент рендерит `HomeAndConstructionBusiness` (на главной и через `layout.tsx` метаданные), `Service` (на каждой странице `appliance-repair/[slug]`, уже есть паттерн в текущем HTML — просто переносится), `FAQPage` (везде, где есть `FaqAccordion`), `AggregateRating`/`Review` только из реальных отзывов в `data/reviews.ts`. Все — из `data/business.ts` как единого источника NAP, что закрывает находку п. 1.3.
- **areaServed ≤ 20:** `data/business.ts` содержит canonical-список зон обслуживания, синхронизированный с реальным GBP-профилем (не более 20, см. Часть 3 раздел 2) — используется и в schema, и (опционально, шире, текстом) на страницах — но структурно это один список, а не 26 захардкоженных городов в одном файле и другой список в другом.
- **Core Web Vitals:** SSG по умолчанию + `next/image` + минимум клиентского JS в hero (текущий `js/main.js` — это лёгкий vanilla JS для nav/формы/скролл-трекинга, переносится как клиентский компонент без блокировки LCP) — закрывает требования Части 1 (раздел 7.3) и Части 3 (раздел 4) архитектурно, без отдельной оптимизационной задачи после запуска.
- **Sitemap/robots:** `app/sitemap.ts` строится из `data/services.ts` + `data/towns.ts` (только `isFullPage`) + статических роутов — устраняет находку п. 1.2 структурно.
- **Canonical/domain:** используется значение из `data/business.ts` (`siteUrl`), которое обязательно подтвердить с владельцем до продакшен-сборки (см. п. 1.3) — не хардкодить `ekfix.us` по всем файлам вручную, как сейчас.

## 6. Что НЕ входит в этот этап (осознанно вне периметра автопилота)

- Полноценная система онлайн-записи с реальными слотами (Housecall Pro/Jobber или кастом) — решение и подключение остаётся за владельцем, на этом этапе достаточно рабочей отправки заявки (п. 1.1).
- Фирменная скролл-анимация hero (Часть 1, раздел 6) — отдельное усиление, не блокирует SEO/B2B-приоритет, можно делать отдельным заходом.
- Полная матрица город×услуга и остальные 18+ городских страниц сверх топ 5-8 — сознательно не создаются (anti-doorway правило).
- Реальные шаги вне кода: создание/аудит GBP-профиля, регистрация в цитированиях/каталогах, вступление в Charlotte Chamber of Commerce, сбор новых отзывов и коммерческих фото — это офлайн/аккаунтные действия владельца, не задача автопилота.

## 7. Критерии приёмки (дополняют, не заменяют, критерии из Частей 1–2)

- [ ] Визуальное сравнение каждой мигрированной страницы с текущим сайтом — расхождений в вёрстке/стилях нет (кроме двух согласованных расширений CSS из Части 2, раздел 6).
- [ ] Форма заявки реально отправляет данные (email/webhook) — проверено сквозным тестом, не только визуально.
- [ ] `sitemap.ts` на выходе покрывает 100% реально существующих роутов, ни одной страницы не пропущено и не добавлено сверх реально существующих.
- [ ] Название бизнеса, телефон, areaServed идентичны во всех JSON-LD блоках на всех страницах (сверка по `data/business.ts`).
- [ ] `next build` проходит без ошибок, Lighthouse/Core Web Vitals — в зелёной зоне по порогам из Части 3, раздел 4.
- [ ] Ни одна городская страница технически недостижима вне `data/towns.ts` со флагом `isFullPage: true`.
- [ ] Финальный домен подтверждён владельцем и прописан в `data/business.ts` до продакшен-сборки.
