# 0018. JSON-LD — один `@graph` на страницу, стабильные `@id`, в разметке только видимое (дополнение ADR 0007)

## Контекст

ADR 0007 собрал JSON-LD в чистые билдеры `lib/jsonld` (`businessJsonLd`, `serviceJsonLd`,
`faqJsonLd`, `breadcrumbJsonLd`, `aggregateRatingJsonLd`) и один компонент `<JsonLd>`, который
выводил каждый блок отдельным `<script>`. Узлы не имели `@id` и не ссылались друг на друга.
`businessJsonLd()` на главной и страницах городов нёс всё сразу: `image`, `priceRange: "$$"`,
все 20 `areaServed`, `knowsAbout`, `aggregateRating`.

Бриф прогона `entity-commercial-geo` (2026-09-28), 1.3: «Граф JSON-LD со стабильными @id,
построенными от data/business.siteUrl»; одна сущность бизнеса `HomeAndConstructionBusiness`
(«отдельный дублирующий Organization-узел не нужен»); `WebSite` с `publisher` → бизнес;
`Person` владельца; `Service` с `provider` → бизнес; `Article` с `author` → Person;
«FAQPage и BreadcrumbList — как сейчас»; «Разметка описывает только то, что видно на
странице»; «AggregateRating — только по реальным отзывам на сайте». Владелец — Constantin,
фамилия не публикуется.

## Решение

- **Узлы и граф.** `lib/jsonld` — чистые функции-узлы без `@context` и сборщик
  `graph(...nodes)` → `{ "@context": "https://schema.org", "@graph": [...] }` (`null`-узлы
  отбрасываются). `<JsonLd data={graph(...)}>` принимает только граф и выводит **один**
  `<script type="application/ld+json">` на страницу.
- **Стабильные `@id`** от `business.siteUrl` через `lib/seo.absoluteUrl`:
  `ids.business` = `https://ekfix.us/#business`, `ids.website` = `…/#website`,
  `ids.owner` = `…/about#owner`; постраничные — `<url>#service`, `#article`, `#faq`,
  `#breadcrumb`. Узлы ссылаются друг на друга только через `{ "@id": … }`.
- **`businessNode(opts)`** — на каждой странице, базовые поля видны в шапке и подвале всех
  страниц: `name`, `url`, `logo` (`/icon.svg`), `telephone`, `address` (город),
  `openingHoursSpecification`, `sameAs` (3 соцсети из подвала). Поля по странице — только где
  это видно:
  - `image` — только `/` (там фото владельца в hero);
  - `areaServed` — **список мест, показанный на этой странице**: `/` — блок «Where we work»,
    `/towns` — все 20 из `business.areaServed`, город или район — своя зона (район — `Place`,
    город — `City`);
  - `aggregateRating` — только `/` и `/reviews`, строго по `data/reviews.ts` (как в ADR 0007);
  - `knowsAbout` — только коммерческий хаб.
- **Убрано:** `priceRange` (диапазон цен на сайте нигде не показан); `legalName` удалён из
  `Business`; `alternateName` не выводится — юрназвание не подтверждено владельцем.
- **Прочие узлы:** `websiteNode()` — только `/`, `publisher` → бизнес. `ownerNode()` полностью —
  только на `/about`: `name: "Constantin"`, `jobTitle`, `worksFor` → бизнес, `image`,
  `knowsAbout` и два `hasCredential` (EPA Section 608 Universal, OSHA) — каждая строка дословно
  видна на `/about`. `serviceNode()` — на 12 страницах услуг и 7 коммерческих дочерних,
  `provider` → бизнес, `areaServed` = места из H1. `articleNode()` — `author` → владелец,
  `publisher` → бизнес; бросает исключение на черновике и на статье без `reviewedByOwner`.
  `faqNode()` отбрасывает черновые пункты и возвращает `null`, если опубликованных нет.
  `breadcrumbNode()` — из того же трейла, что видимые крошки (`lib/breadcrumb`).

## Почему

- **Отдельные блоки без `@id`** (как в ADR 0007) — отвергнуто брифом: без стабильного `@id`
  поисковику и ИИ-ассистенту приходится угадывать, что бизнес на двух страницах — одна сущность.
- **Отдельный узел `Organization` рядом с `LocalBusiness`** — отвергнуто брифом: одна сущность,
  без дубля.
- **Все поля бизнеса на каждой странице** (как было) — отвергнуто правилом «только видимое»:
  `priceRange` не виден нигде; `areaServed` из 20 городов на странице, где их нет, и
  `aggregateRating` по 6 отзывам на странице города, где показаны 3, — это данные не со
  страницы.
- **`areaServed` как флаг «вкл/выкл»** (исходная сигнатура в спецификации §4) — заменено списком:
  на разных страницах видны разные наборы мест, и разметка должна совпадать именно с ним.
- **Полный `Person` на каждой странице** — отвергнуто: должность, сертификаты и `knowsAbout`
  видны только на `/about`; остальные страницы ссылаются на владельца по `@id`.
- **Библиотека `schema-dts`** — отвергнуто по той же причине, что в ADR 0007: узкие билдеры под
  тестом дешевле зависимости.

## Последствия

- ADR 0007 дополнен: билдеры и единственный компонент остались, но старые функции
  `*JsonLd()` заменены узлами, а вывод — одним графом.
- Шов 3 переписан (`lib/jsonld.test.ts`): `@id` и ссылки на бизнес, Person без фамилии,
  `articleNode` бросает на непроверенной статье, `businessNode()` без опций не содержит
  `areaServed`/`aggregateRating`/`priceRange`. QA-скрипт прогона сверяет строковые значения узлов
  с видимым текстом страницы.
- Любое изменение видимого (убрали отзывы со страницы, сменили список мест) обязано менять и
  опции `businessNode` на этой странице — связь держится дисциплиной страницы, а не типом.
- Новый тип страницы добавляет свой узел в `graph(...)`, а не второй `<script>`.
- `sameAs` расширится, когда появятся видимые на сайте профили GBP/Yelp/BBB/Nextdoor (факт 12).
